# Deployment

Two scripts, run in this order. `ec2.sh` reads the database endpoint and secret ARN
from the RDS instance, so the database has to exist first.

```bash
./deploy/rds.sh provision
```

```bash
./deploy/ec2.sh provision
```

Both are idempotent — re-running reuses whatever already exists — and both have a
`teardown` that requires typing the resource name to confirm.

## IAM permissions

The scripts need EC2, RDS and Secrets Manager access on your IAM user, plus a small set
of IAM permissions so `ec2.sh` can create the instance role.

For the first three, attach the AWS managed policies `AmazonEC2FullAccess`,
`AmazonRDSFullAccess` and `SecretsManagerReadWrite`.

For the IAM permissions, prefer [`iam-policy.json`](iam-policy.json) over
`IAMFullAccess`. `IAMFullAccess` would let a long-lived access key on your laptop create
any role in the account; this grants only the calls the scripts actually make, and only
for resources whose names begin with `fixed-income-`.

```bash
aws iam put-user-policy --user-name YOUR_IAM_USER --policy-name fixed-income-deploy --policy-document file://deploy/iam-policy.json
```

Run that from the repository root — the `file://` path is relative to your working
directory, not to the policy file.

**`iam:PassRole` is the permission people miss.** Launching an instance with an instance
profile requires permission to *hand that role to EC2*, separately from permission to
create it. Without it, `run-instances` fails with an authorization error that does not
mention `PassRole`. It is included above, conditioned on being passed to
`ec2.amazonaws.com` and to project roles only.

Note that IAM policy documents accept only `Version`, `Id` and `Statement` at the top
level — a stray comment key is rejected as `MalformedPolicyDocument`, which is why the
explanation lives in this file rather than in the JSON.

## What gets created

| Resource | Name | Notes |
|---|---|---|
| RDS instance | `fixed-income-db` | `db.t4g.micro`, 20GB gp3, **not** publicly accessible |
| Secrets Manager secret | RDS-managed | password generated by AWS; no human sees it |
| DB security group | `fixed-income-db-sg` | Postgres from the app security group only |
| IAM role | `fixed-income-app-role` | SSM access + read of that one secret ARN |
| Instance profile | `fixed-income-app-profile` | |
| App security group | `fixed-income-app-sg` | port 80 inbound; **port 22 never opened** |
| EC2 instance | `fixed-income-app` | `t3.micro`, Amazon Linux 2023, IMDSv2 required |

Roughly **$22/month** (RDS ~$14.40, EC2 ~$7.50, secret ~$0.40). On an account past its
first 12 months none of this is free tier.

## Operating it

```bash
./deploy/ec2.sh url
```

```bash
./deploy/ec2.sh logs
```

```bash
./deploy/ec2.sh redeploy
```

There is no SSH key and port 22 is closed. Shell access, log tailing and redeploys all
go through SSM Session Manager, authenticated by IAM. For an interactive shell:

```bash
aws ssm start-session --target "$(aws ec2 describe-instances --filters 'Name=tag:Name,Values=fixed-income-app' 'Name=instance-state-name,Values=running' --query 'Reservations[0].Instances[0].InstanceId' --output text)"
```

## Tearing it down

Order does not matter, but do both — they are billed separately.

```bash
./deploy/ec2.sh teardown
```

```bash
./deploy/rds.sh teardown
```

RDS instances can also be **stopped for up to 7 days** at a stretch if you want to pause
the meter without destroying the data:

```bash
aws rds stop-db-instance --db-instance-identifier fixed-income-db
```

## Troubleshooting

**The app returns 503 with a configuration error.** That is the intended failure mode,
not a crash: the WSGI entry point reports why it could not build rather than leaving
gunicorn to say "application object must be callable". The message names the missing
variable. `./deploy/ec2.sh logs` shows it.

**Bootstrap takes 2–4 minutes after the instance reaches `running`.** It installs
Python 3.11, clones the repo, creates a venv, loads the data, then starts the app. Poll
for readiness:

```bash
until curl -sf "$(./deploy/ec2.sh url)/healthz"; do sleep 15; done
```

**The instance cannot reach the database.** `ec2.sh provision` authorises Postgres from
the app security group, but only if `fixed-income-db-sg` exists — so if you created the
database another way, add the rule yourself. Check with:

```bash
aws ec2 describe-security-groups --filters Name=group-name,Values=fixed-income-db-sg --query 'SecurityGroups[0].IpPermissions'
```

**`git clone` fails during bootstrap.** The user-data clones over HTTPS with no
credentials, so the repository must be publicly readable at deploy time. If it is
private, either make it public temporarily or bake the code into a custom AMI — do not
put a token in user-data, which any process on the instance can read from the metadata
service.
